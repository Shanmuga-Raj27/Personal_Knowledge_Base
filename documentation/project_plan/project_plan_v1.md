# Production AI File Semantic Search — Implementation Plan

This document outlines the production-ready architecture and implementation plan for adding AI-powered semantic file search to the Personal Knowledge Base application. It uses the official Google GenAI Python SDK (`google-genai`) and the modern Qdrant client interfaces.

---

## 1. High-Level Architecture

The system treats MySQL as the single source of truth for metadata and files, using Qdrant purely as a searchable vector index.

```text
       React Client
         │     ▲
  Search │     │ Ranked
   Query │     │ Results
         ▼     │
  ┌────────────────────────────────────────────────────────┐
  │ FastAPI Backend (Coordinator)                          │
  │                                                        │
  │ 1. Receives Query string                               │
  │ 2. Requests embedding vector from Google GenAI API     │
  │ 3. Performs similarity search query to Qdrant          │
  │ 4. Receives matching point IDs and scores from Qdrant  │
  │ 5. Retrieves authoritative metadata rows from MySQL     │
  │ 6. Returns sorted metadata + score results to Client   │
  └─────┬────────────────────────────────────────────▲─────┘
        │                                            │
        │ Generate Embedding                         │ Fetch Authoritative
        ▼                                            │ Metadata by ID
  ┌──────────────────────────┐                 ┌─────┴─────────────┐
  │ Google GenAI API         │                 │ MySQL Database    │
  │ (gemini-embedding-2)     │                 │ (Source of Truth) │
  └──────────────────────────┘                 └───────────────────┘
        │                                            ▲
        ▼ Return Vector (768d)                       │
  ┌──────────────────────────────────────────────────┘
  │ Qdrant Vector DB (Searchable Index)
  │ (Matches similarity, returns Point ID = file_id)
  └──────────────────────────────────────────────────┘
```

### Component Responsibilities

1. **React Frontend**: Captures search terms, coordinates visual feedback states (loading skeletons, results list, fallback warnings), and triggers API requests.
2. **FastAPI Backend**: Orchestrates API key handling, coordinates rate limits/retries, calls Google GenAI for vector embeddings, queries Qdrant for matched indexes, and fetches MySQL records.
3. **Google GenAI API**: Converts natural language text blocks into dense float vector representations.
4. **Qdrant Vector DB**: Indexes vectors inside collections, performs high-performance Cosine similarity matching, and supports payload metadata filtering.
5. **MySQL Database**: Stores the canonical authoritative metadata (filenames, custom descriptions, creation dates, tags).

## 2. Data Model

### MySQL: Authoritative Table (`file_metadata`)
Remains the primary record container. Qdrant references this schema via `fileid`.

| Column | Type | Description |
| :--- | :--- | :--- |
| `fileid` | `INTEGER` | Primary Key (Auto-Increment) / Map anchor for Qdrant `Point ID` |
| `s3_key` | `VARCHAR(255)` | Unique S3 storage locator key |
| `filename` | `VARCHAR(255)` | Original user file name |
| `title` | `VARCHAR(100)` | Document Title |
| `description` | `VARCHAR(255)`| Document summary |
| `tags` | `VARCHAR(100)` | Comma-separated list of keywords |

### Qdrant: Vector Point Schema
Stores the floating-point vector along with search payload filters.

* **Point ID**: `file_id` (Mapped to MySQL primary key, represented as standard integer IDs in Qdrant).
* **Vector**: `[float; 768]` (The 768-dimension floating-point embedding generated by Gemini).
* **Payload**:
  ```json
  {
    "file_id": 42,
    "filename": "aws-architecture.pdf",
    "title": "AWS Architecture",
    "tags": "aws, cloud, backend",
    "description": "Architecture notes for S3 and FastAPI"
  }
  ```

## 3. Metadata Embedding Strategy

Initially, search indexes are generated using **Metadata Semantic Search** (one embedding per file, constructed from structured descriptive attributes). Full-document parsing, chunking, and internal content retrieval are reserved for future phases.

### Structured Text Normalization Template
Prior to generating the embedding vector, the metadata fields must be compiled into a standardized plain text block to ensure consistent vector representation:

```text
Title: AWS Architecture
Description: Architecture notes for S3 and FastAPI
Tags: aws, cloud, backend
Filename: aws-architecture.pdf
```

## 4. Gemini Configuration

We utilize the official, modern Google GenAI SDK (`google-genai`) for Python to generate vectors.

### Configuration Parameters
* **SDK Library**: `google-genai` (do not use legacy `google-generativeai` interfaces).
* **Target Model**: `gemini-embedding-2` (latest unified embedding model).
* **Dimensions**: **768 dimensions** (explicitly configured via `output_dimensionality` parameter to optimize storage footprint and query speeds).
* **Initialization**: The GenAI client is initialized securely in FastAPI:
  ```python
  from google import genai
  from google.genai import types

  client = genai.Client(api_key=settings.GEMINI_API_KEY)
  ```

## 5. Qdrant Collection Design

A single, optimized collection will be declared in Qdrant for the personal knowledge-base indexing:

* **Collection Name**: `document_vault`
* **Vector Configuration**:
  * **Size**: `768` (must exactly match Gemini's configured output dimensions).
  * **Distance Metric**: `Distance.COSINE` (standard Cosine similarity metric for semantic matching).
* **Payload Fields**: `file_id`, `title`, `filename`, `tags`, `description`.
* **Payload Indexing**:
  * Create a payload index on `tags` as a `KEYWORD` schema for fast hard-filtering during similarity scans.
  * *Filtering Principle*: Heavy categorical matching (e.g. searching only files tagged "finance") should be passed as Qdrant filters during the `query_points` phase, rather than filtering raw results post-query in Python.

## 6. File Indexing Flow

When a user uploads a new document, it goes through the following sequence:

```text
User Uploads File 
       │
       ▼
File stored in S3 & Metadata stored in MySQL (file_id is generated)
       │
       ▼
Build structured metadata text string
       │
       ▼
Generate Gemini Embedding (Client.models.embed_content)
       │
       ▼
Upsert Vector into Qdrant (client.upsert with Point ID = file_id)
```

### Exception & Fail-Safe Strategy
* **Gemini Embedding Fails**: Log error. MySQL record status remains `active`, but a background flag `is_indexed` is marked `0`. The API returns a `200 OK` for the file upload but schedules a retry job.
* **Qdrant Upsert Fails**: Revert or mark the file as unindexed in MySQL. Throw a handled warning.
* **Retry Strategy**: Implement a background cron worker that queries MySQL for `status = 'active' AND is_indexed = 0` and attempts to regenerate embeddings and sync to Qdrant with exponential backoff (up to 5 retries).
* **Idempotency**: Qdrant `upsert` automatically updates existing points if the `file_id` already exists, preventing duplicate vectors.

---

## 7. Metadata Update Flow

When a user edits the Title, Description, or Tags of a file:

```text
User edits details ──► Update MySQL ──► Build updated text ──► Regenerate embedding ──► Upsert to Qdrant
```

* **Stale Vector Prevention**: Because Qdrant `upsert` overrides the point with the specified `id`, using the MySQL `file_id` as the Qdrant point ID prevents stale vectors from duplicating or lingering in memory.
* **Failure Reconciliation**: If the Qdrant update fails after MySQL saves, mark `is_indexed = 0` in the database to allow the background worker to sync the vector asynchronously.

---

## 8. Delete Flow

When a document is deleted from the vault:

```text
Delete request ──► Delete MySQL Record (Authoritative) ──► Delete Qdrant Point (Point ID = file_id)
```

### Reconciliation & Orphans Recovery
* **Partial Deletion Failure**: If MySQL succeeds but Qdrant deletion fails, the vector becomes an "orphan."
* **Self-Healing Index**: When queries return a point ID from Qdrant that no longer exists in MySQL, the system logs the discrepancy, discards the hit, and triggers an asynchronous cleanup call to Qdrant to remove the stale ID.
* **Reconciliation Script**: Provide an administrative endpoint `/admin/reconcile` which fetches all IDs from MySQL and Qdrant, deletes Qdrant points missing from MySQL, and queues indexing for MySQL files missing from Qdrant.

---

## 9. Semantic Search Flow

When the user queries the search bar:

1. **Query Delivery**: React hits `/files/search?q={query}`.
2. **FastAPI Validation**: Strip leading whitespace, validate search length (max 100 characters).
3. **Embedding Generation**: Call Gemini client:
   ```python
   response = client.models.embed_content(
       model="gemini-embedding-2",
       contents=query_string
   )
   query_vector = response.embeddings[0].values
   ```
4. **Qdrant Query**: Call Qdrant using the unified `query_points()` API:
   ```python
   hits = qdrant_client.query_points(
       collection_name="document_vault",
       query=query_vector,
       limit=10
   )
   ```
5. **authoritative Metadata Pull**: Gather matching point IDs (e.g. `[4, 12, 19]`), run a single batch SQL lookup:
   ```sql
   SELECT * FROM file_metadata WHERE fileid IN (4, 12, 19)
   ```
6. **Ranking & Delivery**: Order the database rows matching Qdrant similarity scores and return the ranked payload to React.

### Search Criteria Settings
* **Result Limit**: Default to 10 points.
* **Minimum Similarity Score**: Default to `0.55` (Cosine similarity threshold to filter irrelevant hits).
* **Empty Queries**: If query string is empty, skip embeddings/Qdrant and perform the standard DB fetch to return all active files.

## 10. Fallback Search Flow

If the Gemini API or Qdrant Vector database is offline or timed out, the system automatically degrades to the local case-insensitive substring search to maintain availability.

```text
                       User Enters Search Query
                                  │
                       ┌──────────┴──────────┐
                       ▼                     ▼
               Gemini/Qdrant ONLINE   Gemini/Qdrant OFFLINE
                       │                     │
                       ▼                     ▼
                Semantic Search        Degrade to Local
               (Similarity List)       Substring Filter
```

* **No Matches Notification**: If semantic search runs but returns nothing above the similarity threshold, output: *"No semantic matches found. Displaying keyword search results instead."* and trigger the fallback keyword filter.

---

## 11. Embedding Model Migration Strategy

If Google updates the embedding model (e.g. releasing a new version or changing dimension structures):

```text
Model Migration ──► Create new collection (e.g. v2) ──► Re-generate embeddings for active files ──► Swap aliases
```

Changing embedding models or output dimensions will alter the vector space, making Cosine comparisons between old and new vectors invalid.
* **Alias Strategy**: Point the code to an alias (e.g. `document_vault_active`). When migrating, index files into `document_vault_v2` in the background, then swap the alias pointer when indexing completes.

## 13. FastAPI API Design

Ensure clean integration using only necessary REST endpoints:

* `POST /files/upload-complete`: Handles database creation, generates Gemini embeddings, and indexes vectors inside Qdrant.
* `PATCH /files/{file_id}`: Updates MySQL metadata, regenerates embeddings, and upserts to Qdrant.
* `DELETE /files/{file_id}`: Removes record from MySQL and deletes Qdrant index point.
* `GET /files/search?q=...`: Computes query embeddings, queries Qdrant via `query_points()`, resolves authoritative metadata from MySQL, and executes local fallback searches on failures.

## 14. Production Reliability Considerations

### Rate-Limits & Retries
Wrap Gemini embedding calls inside a retry handler with exponential backoff to recover from `429 Too Many Requests` rate limits:
```python
import time
from google.genai.errors import APIError

def embed_with_retry(client, text, model="gemini-embedding-2", retries=3, delay=1):
    for i in range(retries):
        try:
            return client.models.embed_content(
                model=model,
                contents=text,
                config=types.EmbedContentConfig(output_dimensionality=768)
            )
        except APIError as exc:
            if exc.code == 429 and i < retries - 1:
                time.sleep(delay * (2 ** i))
                continue
            raise exc
```

### Latency Logging
Log latency metrics for both Gemini (`embed_content`) and Qdrant (`query_points`) to detect bottleneck thresholds.

## 16. Code Examples (Python Client v1.10+)

### 1. Gemini Client Initialization
```python
from google import genai

client = genai.Client(api_key=settings.GEMINI_API_KEY)
```

### 2. Document/Query Embedding Generation
```python
from google.genai import types

# Document context embedding
doc_response = client.models.embed_content(
    model="gemini-embedding-2",
    contents="Title: File Title\nDescription: Context summary",
    config=types.EmbedContentConfig(output_dimensionality=768)
)
doc_vector = doc_response.embeddings[0].values

# Query text embedding
query_response = client.models.embed_content(
    model="gemini-embedding-2",
    contents="Find notes about S3 storage",
    config=types.EmbedContentConfig(output_dimensionality=768)
)
query_vector = query_response.embeddings[0].values
```

### 3. Qdrant Collection Creation
```python
from qdrant_client import QdrantClient
from qdrant_client import models

q_client = QdrantClient(url=settings.QDRANT_HOST)

q_client.create_collection(
    collection_name="document_vault",
    vectors_config=models.VectorParams(
        size=768,
        distance=models.Distance.COSINE
    )
)
```

### 4. Qdrant Point Upsert
```python
from qdrant_client.models import PointStruct

q_client.upsert(
    collection_name="document_vault",
    points=[
        PointStruct(
            id=file_id,
            vector=doc_vector,
            payload={
                "file_id": file_id,
                "title": title,
                "filename": filename,
                "tags": tags,
                "description": description
            }
        )
    ]
)
```

### 5. Qdrant Semantic Query (with Filters)
```python
from qdrant_client.models import Filter, FieldCondition

hits = q_client.query_points(
    collection_name="document_vault",
    query=query_vector,
    query_filter=Filter(
        must=[
            FieldCondition(
                key="tags",
                match={"value": "work"}
            )
        ]
    ),
    limit=10
)

for hit in hits.points:
    print(f"ID: {hit.id}, Score: {hit.score}, Payload: {hit.payload}")
```

### 6. Qdrant Deletion
```python
q_client.delete(
    collection_name="document_vault",
    points_selector=[file_id]
)
```

## 17. MVP vs. Future Phase Comparison

### MVP (Metadata Semantic Search)
* **Goal**: Embed document title, tags, description, and filename into a single vector.
* **Pros**: Simple, low-cost, fast execution, highly accurate for catalog search.
* **Limitations**: Cannot search inside PDF or Word contents.

### Future Phase (Full-Document Content Search)
* **Goal**: Extract internal texts from S3 files, partition into chunks (e.g. 500 characters), generate embeddings per chunk, and map queries to specific document excerpts.
* **Requires**: Chunking framework (e.g., LangChain/LlamaIndex), text extractors (PDFMiner, python-docx), and vector index mappings.
